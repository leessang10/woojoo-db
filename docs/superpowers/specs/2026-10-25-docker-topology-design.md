# Docker 리소스 관계도 설계

작성일: 2026-10-25 · 상태: 사용자 검토용

## 목적과 합의

이미지, 컨테이너, 볼륨을 따로 찾아다니지 않고 생성 관계, 접속 포트, 저장 위치와 실행 상태를 한 화면에서 이해한다. 사용자는 ERD 같은 시각화를 요청했고, Compose 프로젝트별 관계도를 기본으로 하며 전체 리소스로 확장하는 방향에 동의했다.

아래 구현 세부 사항과 초기 범위는 이 문서에서 제안하는 기본값이다.

## 접근 방식

- 프로젝트별 관계도 중심: 사용자가 선택한 방향. 컨테이너를 중심으로 이미지, 공개 포트, 마운트, 네트워크를 연결한다. 목록 탐색보다 관계를 이해하기 쉽지만 그래프 밀도를 관리해야 한다.
- 전체 리소스 관계도 중심: 공유 자원과 미사용 자원을 찾기 쉽지만 규모가 커지면 복잡해진다. 보조 보기로 제공한다.
- 리소스별 목록 중심: 단순 관리에는 적합하지만 사용자가 겪는 관계 파악 문제를 해결하기 어려워 기본 화면으로 쓰지 않는다.

연동은 Rust에서 Docker CLI를 호출하는 방식을 제안한다. 기존 AWS CLI 실행 패턴을 참고하고 Docker context와 Compose 설치 환경을 활용한다. Engine API 직접 연동은 별도 전송 계층과 버전 처리가 필요하므로 후속 선택지로 남긴다. Docker 엔진은 별도로 실행되어 있어야 하며, Docker Desktop이나 WSL 엔진 설치·기동 관리는 초기 범위에 포함하지 않는다.

## 초기 범위

1. Docker CLI 및 엔진 연결 상태 확인, context 선택.
2. Compose 프로젝트별 관계도, 독립 컨테이너 그룹, 전체 리소스 보기.
3. 이미지·컨테이너·호스트 공개 포트·볼륨·bind mount·네트워크 관계와 상세 정보.
4. 프로세스 상태와 헬스체크 상태를 구분한 표시, 종료 이유와 최근 로그.
5. 선택한 컨테이너의 실시간 로그, 검색·복사·스크롤 일시정지.
6. 개별 컨테이너 시작·중지·재시작 및 결과 갱신.

이미지 빌드·pull·삭제, 볼륨 삭제·파일 탐색, Compose up/down, 터미널 exec, 다중 컨테이너 통합 로그, DB/API 자동 연결은 후속 범위다. 관계선을 직접 편집해 Docker 구성을 변경하는 기능도 제외한다.

## 화면

앱의 DB/AWS/API와 나란히 Docker 영역을 추가한다. 기존 한국어·영어, 다크·라이트 테마와 공통 컨트롤을 사용한다.

```text
Docker   [연결 대상/context ▼] [새로고침] [마지막 확인 시각]
┌ 프로젝트 ───┬ 관계도 ──────────────────┬ 선택 항목 상세 ┐
│ Compose A   │ 이미지 → 컨테이너 → 볼륨 │ 상태/건강 상태 │
│ Compose B   │ 포트 ───↗       ↘ 폴더   │ 포트/마운트    │
│ 독립 실행   │                 네트워크 │ 종료 이유      │
│ 전체        │ [검색] [맞춤] [자동배치] │ 실행 동작      │
├─────────────┴──────────────────────────┴───────────────┤
│ 선택한 컨테이너 로그  [검색] [자동 스크롤] [복사]         │
└────────────────────────────────────────────────────────┘
```

프로젝트 선택은 context별 마지막 선택을 복원하며, 처음에는 첫 프로젝트 또는 독립 실행 그룹을 선택한다. 전체 보기는 명시적으로 선택한다. 연결된 자원이 없는 빈 상태와 조회 실패를 구분한다.

클릭한 노드의 직접 연결을 강조하고 나머지는 흐리게 표시한다. 노드와 선의 의미를 범례로 설명하며 색상만으로 상태를 전달하지 않는다. 상세 패널은 목록에서도 키보드로 접근할 수 있게 한다. 새 데이터가 와도 기존 위치와 줌을 유지하며 자동배치는 명시적 버튼과 최초 로딩에만 수행한다.

## 관계 의미와 식별

- 이미지 → 컨테이너: 생성에 사용한 이미지 ID를 기준으로 연결하고 태그는 표시 이름으로 사용한다. 태그 변경이나 이미지 부재를 처리한다.
- 호스트 포트 → 컨테이너: 호스트 주소, 호스트 포트, 컨테이너 포트, TCP/UDP를 표시한다. 예: `127.0.0.1:15432 → 5432/tcp`. EXPOSE만 있고 실제 publish가 없으면 `컨테이너 내부 포트 · 호스트 미공개`로 표시한다.
- `0.0.0.0`와 `::`는 바인딩 주소다. 접속 가능성이나 HTTP 서비스임을 뜻하지 않는다. 원격 context를 `내 PC`라고 표시하지 않고 `Docker 호스트`라고 표시한다. host 네트워크 모드는 별도 설명하며 없는 포트 매핑을 만들어내지 않는다.
- 컨테이너 → volume: 볼륨 이름, 컨테이너 내부 대상 경로, 읽기 전용/쓰기 가능을 표시한다. 익명 볼륨도 실제 이름과 ID로 식별한다.
- 컨테이너 → bind mount: Docker 호스트의 소스 경로와 컨테이너 내부 경로를 구분한다. 원격/WSL 호스트 경로를 Windows의 로컬 경로로 해석하지 않는다.
- tmpfs: 메모리 임시 마운트로 표시하며 영구 볼륨과 구분한다.
- 컨테이너 → 네트워크: 네트워크 소속을 표시한다. 같은 네트워크 소속은 실제 통신 성공이나 서비스 의존 관계를 보장하지 않는다.

Compose의 프로젝트·서비스 라벨로 컨테이너를 묶는다. Compose 파일은 읽거나 실행하지 않는다. 프로젝트에 연결된 공유 자원은 해당 뷰에 포함하고, 상세에서 모든 사용 컨테이너와 다른 프로젝트 소속도 표시한다. 전체 보기에는 엔진이 반환한 미연결 이미지와 볼륨도 포함하되 `현재 컨테이너 참조 없음`으로만 표현한다. 삭제해도 안전하다고 판단하지 않는다. 프로젝트 라벨이 있는 볼륨/네트워크만 남아 있는 경우도 프로젝트 목록에 표시한다.

노드 키는 context + 자원 종류 + 안정적인 ID(또는 볼륨 이름)로 구성한다. 같은 마운트 대상에 여러 관계가 있거나 같은 포트를 여러 주소에 바인딩한 경우 각 관계를 보존한다.

## 상태 판정

프로세스 상태(created/running/paused/restarting/exited/dead 등)와 건강 상태(starting/healthy/unhealthy/미설정)를 독립적으로 표시한다.

| 관측 | 표시 |
| --- | --- |
| running + healthy | 실행 중 · 헬스체크 통과 |
| running + unhealthy | 실행 중 · 헬스체크 실패 |
| running + starting | 실행 중 · 헬스체크 준비 중 |
| running + 헬스체크 없음 | 실행 중 · 서비스 정상 여부 미확인 |
| restarting | 재시작 중 · 재시작 횟수 표시 |
| exited + 0 | 종료됨 · 종료 코드 0 (작업 완료 가능) |
| exited + 비영 코드 | 종료됨 · 종료 코드 및 엔진 오류 표시 |
| OOMKilled | 메모리 부족으로 종료된 기록 표시 |
| 연결 실패/오래된 데이터 | 상태 확인 불가 · 마지막 확인 시각 |

재시작 횟수 하나만으로 `재시작 반복`이라고 단정하지 않는다. 초기에는 엔진의 restarting 상태와 횟수를 그대로 보여준다. 로그의 ERROR 문자열은 검색 대상으로만 사용한다. 헬스체크 결과, 종료 시각, 엔진 오류와 최근 로그를 상세에서 함께 확인한다. 과거 OOM 기록과 현재 상태를 혼동하지 않는다.

## 데이터와 실행 구조

프런트엔드 `src/docker/`에 모델·API 어댑터·관계도·상세·로그·스타일을 분리한다. React Flow와 Dagre를 사용하되 DB 전용 ERD 문서/변경 로직과 결합하지 않는다. `App.tsx`에 Docker 영역을 통합한다.

Rust `src-tauri/src/docker/`에 CLI 실행, 조회/정규화, 로그 구독, 컨테이너 동작을 둔다. `main.rs`에 명령과 수명 관리 상태를 등록한다. CLI에서 구조화된 JSON 결과를 받아 필요한 필드만 프런트엔드에 전달한다. inspect 원문과 환경변수 전체는 노출·저장하지 않는다.

- 명령은 셸 문자열이 아닌 실행 파일 + 개별 인수로 전달하고, 모든 명령에 선택된 context를 명시한다. 전역 `docker context use`는 실행하지 않는다. 충돌하는 Docker 연결 환경변수를 정리해 선택 대상이 실제 실행 대상과 일치하도록 한다.
- 각 요청은 context와 요청 세대 ID를 포함한다. context 전환 후 늦게 도착한 결과나 로그는 새 화면에 적용하지 않는다.
- 조회는 실행 시간·출력 크기·동시 실행 수를 제한한다. Windows에서는 콘솔 창을 띄우지 않는다. 컨테이너가 조회 중 사라진 경우 부분 오류로 처리한다.
- 화면이 보일 때 상태를 약 5초마다 갱신하고 구조 목록은 약 30초마다 갱신한다. 수동 새로고침과 실행 동작 직후에는 모두 갱신한다. 중복 폴링은 금지하며 숨겨진 영역에서는 폴링과 로그 구독을 종료한다.
- context 변경, 선택 변경, 화면 숨김/종료 시 로그 프로세스와 구독을 정리한다. 구독 ID 기반으로 이전 세션의 정리 요청이 새 구독을 중지하지 못하게 한다.
- 로그는 최근 200줄로 시작하고 후속 출력을 스트리밍한다. 메모리 버퍼는 최대 5,000줄 또는 2MiB로 제한하고 잘린 상태를 알린다. 부분 UTF-8/긴 줄을 처리하고 화면 갱신은 묶어서 전달한다. Docker 로그 명령 실패와 컨테이너의 stderr 로그를 구분한다. 로그 드라이버가 조회를 지원하지 않으면 명시한다.
- Docker CLI 미설치, 엔진 중지/연결 불가, 권한 오류, 지원하지 않는 응답, 부분 조회 실패를 구별한다. 마지막 정상 데이터를 남길 경우 오래된 데이터임을 표시하고 동작을 비활성화한다.

처음에는 context 목록을 지원하되 로컬과 원격을 식별해 표시한다. 원격 context도 CLI가 처리 가능한 경우 동일하게 조회하며 포트 접근이나 호스트 파일 접근을 자동 시도하지 않는다. 브라우저 미리보기에서는 명시적인 데모 자료만 쓰고 실제 연결로 표현하지 않는다.

## 동작과 저장

시작·중지·재시작은 선택된 context와 정확한 컨테이너 ID에만 실행한다. 이름으로 다시 대상을 찾지 않는다. 중복 클릭을 막고 결과를 다시 조회한다. 실행 중인 컨테이너의 중지/재시작은 대상 context·이름을 보여주는 확인을 거친다. 변경 명령은 자동 재시도하지 않는다. 타임아웃이면 실패로 단정하거나 재실행하지 않고 결과 미확정으로 표시한 후 상태를 다시 확인한다.

화면 설정, 선택 프로젝트, 배치와 줌만 context/프로젝트별 저장한다. 로그·환경변수·inspect 응답은 영구 저장하지 않는다. 현재 작업 트리에 존재하는 다른 변경은 그대로 유지하고 관련 통합부만 최소 수정한다.

## 검증과 완료 조건

- 고정 Docker 응답으로 그래프 생성 검증: 공유 이미지/볼륨, bind/tmpfs, 미공개 포트, 다중 바인딩, IPv6/UDP, 독립 컨테이너, 자원만 남은 프로젝트, 누락된 이미지.
- 상태 변환 검증: 헬스체크 미설정/준비/실패, 코드 0 종료, 비영 종료, OOM, 오래된 데이터.
- CLI 테스트: 인수 분리, context 고정, 출력 상한, 타임아웃, 부분 실패, 로그 취소 및 늦은 응답 차단. 동작 테스트는 가짜 실행기로 중복 실행과 자동 재시도 부재를 검증한다.
- UI 테스트: 프로젝트 선택, 관계 강조, 포트/마운트 설명, 로그 전환, 숨김 후 구독 종료, 한국어/영어 및 다크/라이트.
- 실제 Docker가 가능한 환경에서는 테스트 전용 Compose 자원으로 조회·로그·개별 실행 동작을 검증한다. 실제 엔진 검증을 못 하면 그 제한을 보고하고 데모 테스트를 실제 검증으로 표현하지 않는다.

완료 시 사용자는 컨테이너 하나를 선택해 사용 이미지, 공개된 접속 포트, 저장 위치와 마운트 종류, 건강 상태를 확인할 수 있고, 종료 원인과 로그로 이동해 시작·중지·재시작할 수 있어야 한다.

## 구현자에게 위임한 사항

세부 컴포넌트 분해, DTO 이름, 그래프 간격, 노드 아이콘과 색상, CLI JSON 명령 조합은 위 의미와 동작을 유지하는 범위에서 결정한다. 대규모 그래프는 검색/종류 필터와 표시 제한을 제공하되 생략 사실과 수를 명시한다.
