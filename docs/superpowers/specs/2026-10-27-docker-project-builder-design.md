# Docker 프로젝트 조립·검토 작업 공간 설계

작성일: 2026-10-27 · 상태: 구현자 관점 검토 반영 완료, 상세 설계 제안

## 1. 의도와 확정된 요구

사용자는 Docker 세부 문법을 외우지 않고 프로젝트에 필요한 컴포넌트를 선택하고 연결한다. 구성과 실행 결과를 같은 작업 공간에서 확인한다. Redis 하나를 로컬에서 사용하기, Nest API + MySQL + Redis + Elasticsearch + Client 환경 구성하기, AI가 만든 Compose 파일을 검토하고 수정하기가 동등한 핵심 시나리오다.

사용자가 확정한 내용:

- 이미지 주소를 텍스트로 입력하는 것이 기본 경로가 되어서는 안 된다.
- 프로젝트를 만든 뒤 GUI에서 컴포넌트·네트워크·포트·공유/전용 저장소를 조립한다.
- 컴포넌트 연결 시 필요한 환경 변수와 시작 조건을 자동 제안한다. 사용자가 확인·수정한 뒤 적용한다.
- 기존 Compose 파일도 동일한 GUI에서 구성 관계를 이해하고 수정할 수 있어야 한다.

이하의 초기 범위, 기본값, 저장 정책, 세부 상호작용은 설계자의 제안이다. 사용자 합의로 간주하지 않는다. 2026-10-25 관계도 설계의 조회·상태 의미를 계승하고, 당시 제외했던 관계 편집·Compose 작성 범위를 확장한다.

목표는 색다른 관계도 자체가 아니라 **추가 → 연결 제안 → 검토/수정 → 구성 검사 → 실행 → 결과 확인**을 완결하는 것이다. 운영 목록은 보조 보기이며 프로젝트 조립 캔버스가 기본 작업 화면이다.

## 2. 접근 방식

| 방식 | 장점 | 한계/판단 |
| --- | --- | --- |
| YAML 필드를 폼으로 변환 | 기존 편집기 확장이 간단함 | 관계를 이해하고 조립하려는 요구를 충족하기 어려움 |
| 앱 고유 모델에서 Compose 전체 재생성 | 신규 프로젝트 자동화가 쉬움 | 가져온 파일의 주석·확장 필드·고급 기능 손실 위험 |
| Compose 원문 + 구조 모델 + 변경 패치 | 신규 조립과 기존 파일 편집을 함께 지원 | 원문 출처 추적과 편집 가능 범위 판정 필요 |

세 번째를 구현 구조로 제안한다. 사용자가 선택한 제품 동작은 **자동 제안 후 확인·수정**이며, 원문 보존을 위한 내부 구조는 설계자 선택이다. React/TypeScript, shadcn/Radix, React Flow, Rust/Tauri, Docker CLI를 유지한다.

## 3. 초기 완성 범위

- Windows 앱 + 로컬 Docker Linux 컨테이너 환경을 대표 완료 환경으로 삼는다. 기존 원격 context 조회·운영 기능은 유지한다.
- Redis·MySQL·PostgreSQL·Elasticsearch 카탈로그, 공개 Docker Hub 이미지 검색/태그 선택, 로컬 이미지 선택, 기존 Dockerfile 기반 내 앱 추가를 포함한다.
- 단일 Compose 파일 GUI 읽기/쓰기, 네트워크·마운트·포트·환경 변수·healthcheck·depends_on·기본 build 설정을 포함한다.
- 다중 Compose 파일은 순서를 명시해서 합성 구성 검토를 지원한다. 초기에는 원본 파일별 YAML 편집과 전체 재검증을 제공하고, 병합 결과에 대한 GUI 쓰기는 제한한다.
- 네트워크 및 볼륨은 프로젝트 내 생성과 기존 외부 자원 선택을 지원한다.
- 새로운 Dockerfile 생성, 소스 코드 자동 수정, 앱 프레임워크별 런타임 설정 주입 코드 생성, Kubernetes/Swarm, 클라우드 배포, 사설 레지스트리 검색/로그인 UI, Dockerfile 없는 소스의 자동 컨테이너화는 후속 범위다.

대표 시나리오를 완성하기 전에는 이미지 종류나 운영 기능을 넓히지 않는다. 정확한 카탈로그 지원 버전은 구현 시 검증한 manifest로 고정하며, 문서에서 최신 버전이나 모든 태그 호환을 약속하지 않는다.

## 4. 화면의 역할과 구조

프로젝트는 실행 전부터 존재한다. 실행 중인 컨테이너만으로 프로젝트 목록을 만들지 않는다.

| 영역 | 역할 |
| --- | --- |
| 프로젝트 사이드바 | 초안/저장한 프로젝트/실행 중 프로젝트, Compose 가져오기, 새 프로젝트 |
| 상단 | 프로젝트명, Docker 대상, 초안·저장·실행 상태, 구성 검사, 실행/변경 적용 |
| 중앙 캔버스 | 서비스 컴포넌트와 관계 편집, 검색, 화면 맞춤, 되돌리기/다시 실행 |
| 오른쪽 속성 패널 | 선택한 컴포넌트·연결·네트워크·저장소 설정. 선택 전에는 접힘 |
| 하단 도구 패널 | 문제 목록, 변경 검토, 진행 상황, 로그, Compose 원문. 사용자가 열 때 표시 |
| 컴포넌트 추가 패널 | 카탈로그·이미지 검색·로컬 이미지·내 앱. 선택 후 중앙으로 복귀 |

전체 화면 마법사와 단계마다 모든 서비스의 모든 필드를 나열하는 폼을 없앤다. 고급 설정은 해당 항목 안에서 펼친다. 속성/하단 패널은 크기 조절·접기가 가능하고 선택한 노드는 패널 개폐 후에도 보이게 한다. 960×640에서는 전체 패널을 강제로 동시에 펼치지 않는다.

새 프로젝트는 기본 이름을 가진 초안으로 즉시 생성된다. 이름은 인라인 수정하고, 폴더는 처음 저장/실행할 때 제안한다. 엔진이 꺼져 있어도 초안 작성·정적 검토가 가능하다. Docker CLI 검증이나 실행이 필요할 때 해당 상태를 설명한다.

## 5. 컴포넌트 추가

### 5.1 카탈로그

카드는 제품 이름, 역할, 공급자, 이미지 저장소, 선택 버전, 지원 플랫폼, 로컬 다운로드 여부를 보여준다. `추가`는 초안에 노드를 넣는 동작이며 pull이나 실행이 아니다.

템플릿은 단순 이미지 문자열이 아니라 버전별 설정 지식이다. 이미지/지원 버전, 제공 endpoint, 필수 입력, 데이터 경로, 권한·인증 방식, healthcheck, 접속 변수 후보, 기본 자원 조건, 검증 일자를 포함한다. 설정의 출처는 `템플릿 제안`으로 표시한다. 임의 이미지는 필수 환경 변수·데이터 경로·준비 검사 방법을 자동으로 알 수 없음을 표시하고 직접 편집할 수 있게 한다.

| 컴포넌트 | 기본으로 보여줄 입력/제안 |
| --- | --- |
| Redis | 버전, 데이터 보관 여부, 인증, 내 PC 접속 여부 |
| MySQL/PostgreSQL | 버전, DB 이름, 앱용 사용자, 인증, 전용 데이터 볼륨 |
| Elasticsearch | 버전, 단일 노드 개발 구성, 인증·TLS, 메모리 설정, 전용 데이터 볼륨 |
| 내 앱 | 폴더, 발견한 Dockerfile 선택, build context, 실행 용도, 앱 포트 |

Elasticsearch를 편하게 실행하기 위해 인증/TLS를 몰래 끄지 않는다. 버전별 최소 설정과 연결에 필요한 인증서 참조를 제안하고 필수값만 순차 입력받는다. DB 초기화 계정/비밀번호 변경이 기존 데이터 볼륨 내부의 계정을 자동 변경하지 않는다는 점도 재사용 볼륨 선택 시 설명한다.

### 5.2 검색·버전·오프라인

- 이름 검색 → 저장소 결과 → 태그/플랫폼 선택 → 추가. 사용자가 이미지 표기를 외울 필요가 없어야 한다.
- 검색 결과와 카탈로그를 구분한다. 별표 수를 검증된 템플릿의 신뢰성과 혼동하지 않는다.
- 공개 Hub 검색은 Docker CLI `search` 어댑터, 태그 조회는 공식 Hub API를 사용하는 백엔드 공급자 계층으로 분리한다. 조회 취소·페이지 이동·속도 제한·로그인 필요·오프라인 상태를 처리한다. 비공개 API나 HTML 스크래핑에 의존하지 않는다. [공식 검색](https://docs.docker.com/reference/cli/docker/search/), [태그 API](https://docs.docker.com/reference/api/hub/latest/operations/ListRepositoryTags/).
- 카탈로그는 번들로 제공하여 오프라인에서도 초안 작성이 가능하다. 캐시된 태그는 조회 날짜와 확인 불가를 표시한다. 엔진에 실제 이미지가 없으면 실행 단계에서 다운로드 필요를 알린다.
- 추천 버전은 검증된 태그를 명시한다. `latest`는 자동 기본값으로 두지 않는다. 가져온 태그는 바꾸지 않는다.
- 정확한 재현이 필요하면 digest 고정을 선택할 수 있다. local build는 별도 rebuild 여부를 보여주고 태그 이름만으로 배포 환경과 동일하다고 판정하지 않는다.

## 6. 캔버스 표현

기본 노드는 Compose **service**다. 실제 컨테이너가 생성되기 전에도 이름·이미지/빌드·endpoint·네트워크·설정 미완료 상태가 있다. 실행 후에는 같은 노드에 실제 컨테이너 상태를 덧붙인다. 복제본이 여러 개면 개수를 표시하고 목록으로 펼친다.

전체 화면에 모든 이미지·포트·네트워크·볼륨을 항상 노드로 늘어놓지 않는다. 기본은 서비스와 의도된 접속 관계이고, 네트워크/저장소/시작 조건을 선택해서 상세 관계를 펼친다. 접속선은 `서비스 연결`, 네트워크 참여는 네트워크 배지/멤버십, 볼륨은 별도 저장소 노드와 마운트선, 시작 조건은 텍스트 레이블을 가진 별도 관계로 구별한다. 색만으로 의미를 전달하지 않는다.

한 서비스는 여러 네트워크에 속할 수 있으므로 네트워크 하나의 박스 안에 노드를 넣는 것만으로 모델링하지 않는다. 네트워크 선택 시 멤버와 경계를 강조하고, 저장소 선택 시 공유하는 서비스와 각 경로를 강조한다. 필터가 구성 요소를 숨길 때 숨긴 개수를 표시한다.

접속선을 그리는 것과 네트워크 배지를 추가하는 것은 서로 다른 동작이다. 같은 네트워크에 있다는 이유만으로 모든 서비스 쌍에 접속선을 만들지 않는다. 노드 위치와 선 교차는 실제 네트워크 의미를 바꾸지 않는다.

## 7. 연결 제안의 상세 계약

### 7.1 생성 흐름

1. 소비자 컴포넌트에서 `연결 추가`를 누르거나 endpoint 연결점을 대상으로 드래그한다. 키보드에서는 대상 목록을 사용한다.
2. 제공 서비스의 endpoint를 고른다. MySQL 접속, Redis 접속, HTTP API처럼 protocol·내부 포트를 표시한다.
3. 오른쪽 `연결 설정`에서 네트워크, 전달할 환경 변수, 시작 조건, 추가 변경을 한 묶음으로 제안한다.
4. 사용자는 변수 이름·값·참조·대기 조건을 수정하거나 항목별 제외한다. 기존 값과 충돌하면 기존/제안 값을 비교하며 기본은 기존 값 유지다.
5. `초안에 적용`을 누르면 서비스 설정과 관계가 함께 바뀐다. 실행 중인 컨테이너에는 아직 반영되지 않는다. 한 번의 되돌리기로 전체 제안을 취소한다.

### 7.2 API → MySQL 예시

| 제안 항목 | 예시 | 사용자가 조정할 것 |
| --- | --- | --- |
| 공유 네트워크 | `backend` | 기존 공통망 유지/다른 망 선택/새 망 생성 |
| 접속 호스트 | 서비스 이름 `mysql` | 일반적으로 유지, 별도 alias 사용 가능 |
| 접속 포트 | 내부 포트 `3306` | endpoint가 다를 때 변경 |
| DB/사용자 | MySQL 컴포넌트 설정 참조 | 앱용 DB와 사용자 선택 |
| 비밀번호 | 해당 계정의 secret 참조 | 다른 자격 증명으로 대체 가능 |
| 환경 변수 이름 | `DB_HOST`, `DB_PORT`, `DB_NAME`, `DB_USER`, `DB_PASSWORD` 후보 | 앱에서 실제 사용하는 이름으로 변경 |
| 전달 형식 | 개별 변수 또는 connection URL | 한 가지 기본 형식 선택, URL은 인코딩 처리 |
| 시작 조건 | MySQL 준비 검사 통과 후 시작 | 시작만 대기/대기 없음 등으로 변경 |

NestJS라는 이유만으로 특정 변수 이름을 정답으로 취급하지 않는다. `변수 이름은 앱 설정에 맞게 확인하세요`를 표시한다. 선택한 로컬 폴더의 `.env.example` 등 비밀값 없는 예시 키를 명시적으로 가져와 매핑 후보에 사용할 수 있다. 소스 코드나 실제 비밀값 파일을 외부 AI에 전송하지 않는다. AI 없어도 핵심 연결 기능이 동작해야 한다.

확인된 매핑은 프로젝트에서 다시 사용한다. 제안은 `템플릿`, `예시 파일에서 발견`, `사용자 입력`을 구별한다. 연결이 생성되어도 앱 코드가 그 변수를 읽는다는 보장은 없으며 `구성됨 · 통신 미확인` 상태를 사용한다.

### 7.3 값의 출처·편집·삭제

값은 literal / endpoint 참조 / 컴포넌트 설정 참조 / 프로젝트 변수 참조 / secret 참조를 구분한다. `DB_HOST ← mysql 서비스 이름`처럼 출처를 볼 수 있다. 이 참조는 편집기의 메타데이터이며 내보낸 Compose에는 표준 문법으로 변환한다.

- 서비스 이름·포트 변경 시 참조된 값의 변경안을 보여주고 초안에 함께 반영한다. 문자열 안의 우연히 같은 이름을 일괄 치환하지 않는다.
- 참조 값을 직접 입력으로 바꾸면 `자동 연결 해제`를 표시한다. 이후 템플릿이 덮어쓰지 않는다.
- 연결 삭제 시 그 연결이 생성했고 이후 사용자가 수정하지 않은 변수/depends_on 항목만 삭제 후보로 제시한다. 공유 네트워크 자체나 다른 연결이 사용하는 멤버십은 지우지 않는다.
- 서비스 삭제/이름 변경은 영향받는 연결·마운트·변수·시작 조건을 함께 검토한다. 런타임 데이터 삭제는 별도다.
- 환경 변수가 이미 `env_file` 등에서 오면 우선순위와 편집 대상 파일을 설명한다. 자동으로 더 높은 우선순위 값을 추가하여 기존 설정을 가리지 않는다. `.env`의 치환 값과 컨테이너 환경 변수는 별개로 보여준다. [환경 변수 우선순위](https://docs.docker.com/compose/how-tos/environment-variables/envvars-precedence/).

## 8. 네트워크·포트·시작 조건

### 네트워크

신규 프로젝트에는 기본 프로젝트 네트워크를 제공한다. 추가 서비스가 기본으로 참여하고, UI에는 암묵적인 Compose default network도 표시한다. 연결할 두 서비스가 이미 네트워크를 공유하면 새 네트워크를 만들지 않는다. 공유망이 없으면 어느 쪽을 어떤 네트워크에 추가할지 제안한다. 분리 의도를 확인할 수 있도록 변경 대상을 밝힌다.

외부 네트워크는 실제 Docker 대상에서 선택하고 `외부에서 관리`로 표시한다. 컴포넌트 연결 삭제와 네트워크 자원 삭제는 구분한다. `internal`, `host`, `none`, `service:...` 같은 모드는 일반 bridge 참여와 구별한다. 초기 GUI는 bridge/default/external 편집을 지원하고 특수 모드는 읽기/원문 편집으로 유지한다. [네트워크 동작](https://docs.docker.com/compose/how-tos/networking/).

### 포트와 접속 위치

`컨테이너에서 접속`, `내 PC에서 접속`, `다른 컴퓨터에서 접속`을 구분한다. 앱끼리의 연결에는 내부 포트를 사용하고 호스트 포트를 자동 공개하지 않는다. 단독 Redis를 로컬 도구에서 쓰는 흐름에서는 loopback 공개를 기본 제안한다. DB가 프로젝트에 추가될 때는 내부 전용을 기본 제안하되 `내 PC에서도 접속`으로 공개할 수 있다.

포트 충돌은 같은 호스트의 실제 바인딩을 기준으로 확인한다. 이미 실행 중인 자신의 컨테이너가 사용하는 포트를 무조건 충돌로 보지 않는다. 후보 포트는 제안이며 확보 완료가 아니다. 실행 전 다시 확인한다. TCP/UDP·IPv4/IPv6·바인딩 주소를 보존한다. 원격 context에서는 `내 PC` 대신 `Docker 호스트`이며 로컬 주소를 연결 가능한 주소로 자동 확정하지 않는다.

### Client의 실행 위치

Client 컨테이너가 제공하는 JavaScript가 사용자의 브라우저에서 실행되는 경우 `api:3000`은 브라우저용 접속 주소가 아니다. 연결 설정에서 요청 실행 위치를 `브라우저 / 컨테이너 서버(SSR 포함)`로 구분한다. 브라우저용은 확인된 공개 endpoint 또는 이미 구성된 proxy 경로를 제안한다. 프록시를 자동으로 새로 만들어놓지는 않는다.

환경 변수 전달 시점도 `컨테이너 실행 시 / 이미지 빌드 시`를 구분한다. 빌드 시에는 Dockerfile이 해당 ARG를 사용하는지 확인이 필요하다. 일반 컨테이너 environment를 브라우저 번들 설정으로 자동 취급하지 않는다. 브라우저용 변수에 DB/Redis 비밀번호 등 secret을 연결하지 못하게 한다. SSR과 브라우저 양쪽에서 쓰면 별도 연결 설정을 갖는다.

### 시작 조건

선택지는 `대기 안 함`, `시작 후`, `준비 검사 통과 후`, `작업 성공 종료 후`다. 준비 검사 조건은 대상 healthcheck가 있어야 선택할 수 있다. 알려진 템플릿은 함께 제안하고 임의 이미지는 검증되지 않은 명령을 만들어 넣지 않는다. DAG 순환을 검사한다. 서비스 재시작 정책과 의존 서비스의 최초 시작 조건을 별도 설정으로 표시한다.

`service_healthy`는 시작 전 준비 대기다. 실행 도중 DB 장애의 자동 복구·재접속까지 보장한다고 설명하지 않는다. 일회성 migration은 성공 종료 조건으로 표현한다. [Compose 시작 조건](https://docs.docker.com/compose/how-tos/startup-order/).

## 9. 저장소 조립

저장소 추가에서 `Docker 볼륨 / 호스트 폴더 / 임시 메모리`를 선택한다. 템플릿 DB 데이터는 기본적으로 서비스 전용 볼륨이다. `공유 저장소`는 같은 객체를 여러 서비스에 연결하는 동작이다.

각 마운트는 소스, 컨테이너 대상 경로, 읽기/쓰기, 관리 주체를 표시한다. 호스트 폴더는 로컬 파일 선택기를 사용하되 원격 context에는 선택기 결과를 자동 적용하지 않는다. 이미 선언된 bind path를 가져오면 해당 Docker 호스트 기준으로 읽는다.

저장소 노드를 선택하면 모든 사용자와 각 대상 경로가 보인다. 마운트 제거는 데이터 삭제가 아니다. DB 두 인스턴스가 같은 데이터 디렉터리를 쓰도록 조립하면 템플릿 근거로 경고하되 일반 파일 공유 전체를 오류로 단정하지 않는다. DB 디렉터리를 앱과 공유하는 것을 DB 접속 설정으로 제안하지 않는다.

컨테이너 삭제/재생성, 프로젝트 내리기, 볼륨 데이터 영구 삭제를 서로 다른 동작으로 둔다. 서비스 이름 변경에 따라 기존 데이터 볼륨 이름을 자동 변경하지 않는다. 기존 볼륨은 명시적으로 연결하고 초기화 전제와 버전 호환을 확인하게 한다.

## 10. Compose 가져오기와 원문 보존

가져오기 첫 동작은 원본 읽기와 초안 생성이다. pull/build/up은 하지 않는다. 파일의 상대 경로·env 참조·프로젝트명·profiles·네트워크·볼륨을 읽어 그래프를 만든다. 오류가 있더라도 가능한 부분은 보여주고 위치를 표시한다.

- 원본 YAML Document/CST, 의미 모델, Compose CLI로 해석한 effective model을 분리한다. 기존 `yaml` 패키지의 Document API를 사용하되 주석·anchor 보존은 테스트로 확인한다. [라이브러리 문서](https://eemeli.org/yaml/).
- GUI 변경은 지정한 source path에 패치한다. 전체 object→JSON 재생성으로 원문을 대체하지 않는다. 수정하지 않은 `x-*`, 사용자 지정 설정, 주석은 보존한다.
- anchor/alias/merge를 통해 여러 서비스에 영향을 주는 값은 영향 범위를 표시한다. 초기 GUI에서는 해당 필드 직접 편집을 잠그고 원문 편집으로 이동한다. 모호한 alias를 임의로 펼치거나 공통 anchor를 수정하지 않는다.
- 다중 파일은 입력 파일과 순서를 명시한다. 병합 결과는 Compose CLI를 기준으로 한다. 원본별 YAML 편집은 허용하고 초기 GUI patch는 단일 파일의 명확한 출처에만 허용한다. `include`/`extends` 등 출처를 추적하지 못하는 설정은 제한 항목으로 표시한다. [파일 병합 규칙](https://docs.docker.com/compose/how-tos/multiple-compose-files/merge/).
- 포트·마운트·환경 변수·의존성은 읽은 사실만 표시한다. 같은 망, 비슷한 변수 이름만으로 앱 접속을 확정하지 않는다. 추정 연결은 별도로 제안하며 사용자가 확인해야 관리되는 연결이 된다.
- 외부 편집기에서 원본 또는 참조 env 파일이 바뀌면 오래된 초안임을 알린다. 다시 불러오기/차이 검토/다른 파일로 저장을 제공하며 자동 덮어쓰기하지 않는다.
- 원문 편집 후에는 그래프·문제 목록·연결 메타데이터를 재조정한다. 관리 중인 연결의 값이 바뀌었으면 `외부 수정됨`으로 표시하며 과거 값을 자동 복원하지 않는다.

## 11. 검사와 수정 안내

검사 결과에는 등급, 대상, 근거, 해당 필드, 수정 제안, 자동 확인 가능 여부를 포함한다. 항목 클릭 시 노드/관계/원문 위치로 이동한다.

| 등급 | 예시 | 동작 |
| --- | --- | --- |
| 구성 오류 | 없는 서비스/망/볼륨 참조, 필수 변수 누락, 잘못된 포트, 시작 조건 순환 | 저장 초안은 가능, 유효한 실행 구성 생성까지 적용 차단 |
| 확인 필요 | DB 호스트 공개, 공유 DB 데이터 경로, mutable tag, 새 bind mount, 미확인 변수명 | 구체적인 영향과 수정/유지 선택 |
| 환경 확인 실패 | 엔진 중지, 레지스트리 조회 제한, 권한 부족 | 검증 불가로 표시, 구성 오류나 정상으로 단정하지 않음 |
| 실행 후 확인 | endpoint 통신, 앱의 변수 소비, 준비 검사 미설정 | 상태와 마지막 확인 시간을 표시 |

공유 네트워크 없음은 사용자가 의도한 내부 접속 연결을 만들었을 때 판단한다. 외부 DNS/TLS/프록시를 통하는 정상 구성을 무조건 오류로 처리하지 않는다. 포트·경로의 로컬 검사는 원격 실행 환경의 정상 여부를 보장하지 않는다.

`구성 검사`는 정적 검토 + 설치된 Compose의 capability 검사 + `config` 해석이다. `config`가 통과했다는 이유로 이미지가 존재하거나 앱이 실행될 것이라고 표시하지 않는다. compose config의 normalize 결과는 검증용이며 원문 저장 결과가 아니다. [공식 config 동작](https://docs.docker.com/reference/cli/docker/compose/config/).

## 12. 저장·실행·실패 복구

문서 상태와 런타임 상태는 독립적이다. `초안 변경 있음 / 파일 저장됨 / 실행에 반영되지 않음`과 `엔진 연결 불가 / 미실행 / 실행 중 / 준비 검사 중 / 실패 / 결과 미확정`을 동시에 표현할 수 있어야 한다.

1. `실행` 또는 `변경 적용`을 누르면 저장 위치를 처음 한 번 확인하고 구성 검사를 수행한다.
2. 검토 패널에서 파일 변경과 실행 영향, 대상 context/project, 새 이미지/빌드, 예상 컨테이너 변경, 마운트·외부 노출 변경을 보여준다. 이름 변경에 따른 서비스 교체도 명시한다.
3. 사용자가 `저장하고 실행`을 누르면 검토한 파일을 저장하고 같은 입력을 다시 검증한 뒤 실행한다. 별도 `파일만 저장`도 제공한다.
4. 다운로드/빌드/생성/시작/준비 검사 단계의 출력을 스트리밍한다. 모르는 진행률은 숫자로 만들지 않는다.
5. 실제 snapshot과 health를 재조회해 카드와 문제 목록을 갱신한다. CLI 종료 코드 0과 모든 서비스의 준비 완료는 구별한다.

실행 영향은 Docker/Compose가 실제 결정하는 부분을 포함하므로 사전 표시는 `예상`이다. 신규 또는 변경 서비스, 삭제 후보, 변경 없는 서비스를 비교하되 정확히 판정할 수 없는 경우 이유를 표시한다. 기본 up은 orphan 제거와 볼륨 삭제를 수행하지 않는다. 초안에서 삭제한 서비스의 기존 컨테이너가 남으면 `구성에서 제외됨 · 실행 중`으로 표시하고 명시적 중지/제거 동작을 제공한다.

검토 토큰은 원본 파일 묶음, 읽은 env/config/secret 입력의 revision, resolved configuration, project/context, profile 선택에 결합한다. 저장 뒤 동일한 계획 revision을 확인한다. build context 전체를 불변으로 만들었다고 보장하지 않는다. Dockerfile과 관련 설정의 변경은 감지하며 소스 변경이 빌드 결과에 영향을 준다는 점을 빌드 시각과 함께 기록한다.

작업 중 초안 편집은 허용해도 실행 중 계획은 고정한다. 같은 프로젝트의 중복 실행은 막는다. 화면 숨김/프로젝트 전환은 backend 작업을 중단하지 않는다. 초기 버전에는 앱과 별개 수명의 실행 서비스를 만들지 않는다.

작업 중 앱 종료에서는 `작업 완료까지 기다리기`와 `종료하고 다음에 상태 확인`을 제시한다. 후자를 선택하면 앱이 생성한 CLI 프로세스와 그 자식만 취소·정리하고 작업을 결과 미확정으로 기록한다. Docker daemon 쪽 작업은 계속될 수 있으므로 완료나 rollback으로 간주하지 않는다. 다음 실행 시 context와 Compose 라벨·확보한 컨테이너 ID로 실제 상태를 재조회한다. up/pull/build를 자동 재실행하지 않는다.

복구 기록에는 작업 ID, context/project/source set identity, 비밀값을 포함하지 않는 입력 fingerprint, 단계·시각·결과 코드만 둔다. 원문 명령 출력, resolved 환경 변수, 소스/secret 내용은 저장하지 않는다. 재시작 후 이전 출력 전문은 복원하지 않으며 현재 상태와 다시 얻을 수 있는 컨테이너 로그를 보여준다. UI 관측 중지와 실제 CLI 취소를 구별한다.

기존 고정 180초 실행 제한은 다운로드·빌드를 위한 기본 계약으로 재사용하지 않는다. 취소 가능한 작업 수명 관리와 설정 가능한 제한을 도입한다. 실패하면 성공한 서비스는 유지하고 실패한 노드에서 로그·설정으로 이어진다. 자동 재시도나 자동 rollback/down을 하지 않는다. 설정을 되돌리는 것과 이미 변경된 데이터 복구는 구별한다.

## 13. 비밀값과 파일 정책

- 편집 중 secret은 일반 localStorage, 프로젝트 sidecar, diff, 작업 이력에 저장하지 않는다. 초안 일반 데이터 자동 저장과 secret 보관을 분리한다.
- 초기 기본은 Compose의 변수 참조 + 사용자가 확인한 로컬 env 파일이다. env 파일은 평문임을 알리고 기본 마스킹·출력 제외를 적용한다. 앱 전용 확장 없이 CLI로 실행할 수 있는 구성을 유지한다.
- 새 프로젝트의 비밀값 파일 경로와 `.gitignore` 추가를 저장 검토에 포함한다. 기존 `.env`/`.gitignore`는 덮어쓰지 않고 변경 내용을 보여준다. `.env.example`에는 키와 비밀값 없는 예시만 둔다.
- 파일을 저장하지 않고 종료하면 secret 재입력이 필요할 수 있음을 표시한다. OS vault 보관은 후속 선택지이며 initial scope의 필수 기능으로 잡지 않는다.
- 파일 기반 Compose secrets를 이미 사용하면 보존한다. 지원 템플릿은 이를 제안할 수 있으나 앱이 해당 파일/`_FILE` 관례를 읽는지 확인 없이 변환하지 않는다. Compose secret도 호스트 원본 파일 자체를 암호화하는 기능으로 설명하지 않는다. [Compose secrets](https://docs.docker.com/compose/how-tos/use-secrets/).
- 새 자격 증명은 root 공유 대신 앱용 계정을 기본 제안한다. 실행된 DB의 계정 변경은 Compose 환경 변수 편집만으로 끝났다고 표시하지 않는다.

### 초안 자동 저장의 구체적 경계

임의의 YAML에서 비밀값을 완벽히 탐지할 수 있다는 전제로 설계하지 않는다. 값의 민감도와 자동 저장 여부는 다음 규칙을 따른다.

| 내용 | 자동 저장/복원 |
| --- | --- |
| 화면 배치, 안전하게 분리한 서비스 이름·네트워크 참여·포트·마운트 경로, 매핑의 변수 이름과 참조 ID | 일반 초안/sidecar에 저장 |
| 템플릿이 비밀값 없는 열거형·숫자 등으로 정의한 설정, 사용자가 명시적으로 일반 값으로 지정한 값 | 구조화된 필드 단위로 저장 |
| secret, 분류되지 않은 임의 env 값, command/entrypoint 문자열, build args 값, 자격 증명이 섞일 수 있는 URL | 일반 자동 저장 제외. 재시작 시 값 재입력 필요 표시 |
| 가져온 YAML 원문 또는 원문 편집 내용 | 자동 저장용 복사본/patch/undo를 디스크에 남기지 않음. 원본은 원래 파일에서 읽고 미저장 원문 변경은 메모리에만 유지 |

비밀값으로 표시하지 않았다는 이유만으로 임의 문자열을 일반 값으로 간주하지 않는다. 필드 형태를 검사하는 제한된 serializer가 복원 가능한 항목만 저장한다. 원문 보기에서 작업할 때는 `미저장 원문 변경은 재시작 시 복원되지 않음`을 표시하고, 정상 종료/전환 시 저장 또는 버리기를 선택하게 한다. 사용자가 직접 파일 저장을 선택한 경우에는 검토한 원문과 비밀값 파일을 지정 경로에 저장할 수 있으며, 이는 자동 복원 저장과 별개의 동작이다.

로그는 현재 세션의 제한된 메모리 버퍼로 제공한다. 알려진 비밀값은 마스킹하되 임의 앱 출력 전체의 비밀값 부재를 보장하지 않는다. 자동 작업 기록에는 출력 본문을 넣지 않고, 사용자가 명시적으로 복사/내보내는 동작만 별도로 제공한다.

## 14. 대표 사용자 여정과 완료 조건

### A. Redis 하나 사용

새 프로젝트 → Redis 카드 추가 → 버전·보관·인증과 내 PC 접속 제안 확인 → 실행 검토 → 다운로드/시작 → 확인된 공개 endpoint 및 상태 표시. 전용 볼륨·기본망·준비 검사는 템플릿에서 제안하고 개별 텍스트 입력을 요구하지 않는다. Woojoo Redis 연결로 이동할 때 대상과 인증 전달을 검토하며 실제 연결 성공은 Redis 앱에서 확인한다.

### B. API + MySQL + Redis + ES + Client

인프라 세 개는 카탈로그에서, API/Client 두 개는 자신의 Dockerfile/이미지에서 추가한다. 각각의 로컬 앱이 이미 설정을 읽는다는 가정을 하지 않는다.

API→MySQL/Redis/ES를 연결하고 변수 매핑·secret·공유망·시작 조건을 확인한다. Client→API는 브라우저/SSR 위치와 빌드/실행 시점을 확인한다. DB별 전용 볼륨, 필요할 때만 공유 업로드 폴더를 붙인다. API/Client 외 호스트 공개는 선택 사항이다. 실행 후 하나가 실패하면 해당 카드에서 원인과 수정에 접근한다.

### C. AI가 만든 Compose 검토

가져오기 → 네트워크/마운트/공개 포트/시작 조건과 미해결 변수 표시 → 문제 선택 → GUI 또는 해당 원문 필드 수정 → 파일 차이 검토 → 실행. 알 수 없는 설정을 버리거나 원문을 전체 재작성하지 않는다. 이미지 안의 실제 앱 동작까지 정적 검사로 보증하지 않는다.

## 15. 데이터 모델과 책임

| 객체 | 핵심 데이터 |
| --- | --- |
| ProjectDocument | 안정 ID, 표시 이름, Compose project name, context, source files 순서, base directory, revisions, 선택 profiles |
| ServiceComponent | 안정 ID/Compose key, template+version, image/build, endpoints, env bindings, network memberships, mounts, healthcheck |
| ConnectionIntent | consumer/provider endpoint IDs, 요청 실행 위치, 네트워크 변경, 변수 매핑, 주입 시점, 시작 조건, 항목별 출처/소유권 |
| Network / Storage | Compose key와 runtime identity 분리, managed/external, driver/type/source, 사용자 목록 |
| SourceOrigin | 파일, source path/range, raw expression, effective 값의 마스킹 표현, editable 여부/이유 |
| ChangeSet | 기준 revision, 변경 패치 묶음, 사용자 확인 상태, undo 정보, 영향받는 연결 |
| ValidationIssue | code, severity, 대상 ID/필드, 근거, 제안 fix, 검증 수준 |
| ExecutionPlan / Operation | 입력 fingerprint, 명시적 대상, 예상 동작, 실행 단계, 취소/결과 미확정, 실제 결과 |

프런트엔드는 UI 상태·그래프·undo·제안 편집을 담당한다. Rust는 파일 권한/경로 검증, capability 조회, 실제 CLI config, 계획 fingerprint 재확인, 실행·스트리밍·원격 context 처리의 권위자다. renderer가 전달한 파일 내용이나 계획을 검증 없이 실행하지 않는다.

새 초안은 §13에서 자동 저장을 허용한 구조화된 구성만 앱 데이터 영역에 저장한다. 최초 내보내기 시 표준 `compose.yml`과 선택된 env 파일을 쓴다. 가져온 파일은 원래 폴더를 기준으로 작업한다. 레이아웃·확인된 변수 매핑·안정 ID·템플릿 버전은 기본적으로 앱 데이터의 sidecar에 저장하고 실행을 위한 필수 파일로 만들지 않는다. sidecar가 없으면 그래프를 재구성하고 연결은 미확인으로 돌아간다. 앱에 재등록해도 Compose 자체는 정상 실행 가능해야 한다.

저장·실행·변경 검토의 타깃은 표시 이름이나 현재 선택만으로 정하지 않는다. project ID + context + source set + revision에 결합한다. 읽는 중 사라진 자원, 늦은 응답, 오래된 스냅샷에는 기존 guard를 유지한다.

## 16. 현재 코드에서 바뀌는 부분

| 현재 | 설계 후 |
| --- | --- |
| `ComposeManager.tsx` 대화상자에 마법사·원문·검토·실행 집중 | 프로젝트 편집 화면, 카탈로그, 연결 설정, 검사/실행 패널 분리 |
| `WizardService` 문자열 위주 포트·볼륨·env | 타입이 있는 endpoint/mount/env binding/조건 모델 |
| `composeTopology`에 네트워크 없음 | default/external 포함 멤버십과 접속 관계 분리 |
| preview의 depends는 이름 배열, build는 boolean | depends 조건/옵션, build context/Dockerfile/args, source origin 보존 |
| 원문 전체 편집, 신규 JSON 직렬화 | YAML Document 기반 패치와 Compose CLI 검증 |
| 등록된 파일과 실행 중 프로젝트 목록 분리 | 초안/파일/런타임을 한 프로젝트 ID에 결합 |
| 고정 180초 작업 후 메시지 | 장기 작업 ID, 단계별 출력, 실제 상태 재확인 |

기존 Docker engine/context/snapshot/logs/안전한 삭제/디스크 공간 회수와 공통 UI를 재사용한다. DB 앱의 ERD 데이터 모델에 Compose 의미를 끼워 넣지 않는다. 캐시·관계도 레이아웃 코드 일부는 재사용할 수 있다.

## 17. 검증 기준

아래는 구현 시 필수로 검증할 결과이며 이번 설계 단계에서 수행한 테스트를 뜻하지 않는다.

1. 엔진 없이 새 초안을 만들고 재시작해 복원할 수 있다. 일반 복원 파일에 secret은 없다.
2. Redis 추가·실행에서 이미지 문자열, volume 문법, network 이름을 직접 입력하지 않아도 된다.
3. 공개 Hub 검색·태그 선택과 로컬 이미지 선택이 동작한다. 오프라인/속도 제한에서도 초안을 잃지 않는다.
4. 내 앱은 기존 Dockerfile로 build context를 검토할 수 있다. Dockerfile이 없을 때 미구현 자동 빌드를 약속하지 않는다.
5. API→MySQL 연결은 공유망·변수 매핑·health dependency를 한 changeset으로 추가하고 한 번에 되돌릴 수 있다.
6. 기존 환경 변수, 사용자 수정 값, 다른 연결이 소유한 설정을 덮어쓰거나 삭제하지 않는다.
7. 서비스 이름/포트를 바꾸면 관련 참조만 갱신하고 수동 literal은 유지한다. 연결 삭제 영향도 검토 가능하다.
8. browser Client에는 내부 DNS와 비밀값이 주입되지 않는다. build-time/public와 server runtime 설정을 구분한다.
9. 동일망과 앱 통신 성공, started와 healthy, restart policy와 depends_on을 구별한다.
10. 공유 볼륨의 각 대상 경로/권한, 전용 볼륨, 외부 자원, 원격 bind 경로를 정확히 표시한다.
11. 원본의 주석·미지원 필드·보간 표현을 보존한다. alias/다중 파일의 모호한 GUI 편집은 제한과 원문 경로를 보여준다.
12. 잘못된 구성도 가능한 부분을 표시하고 실제 수정 위치로 이동할 수 있다.
13. 동일 대상의 오래된 preview, 바뀐 env/profile/context, 외부 파일 변경으로 실행이 무효화된다.
14. 실행 전 예상 변경과 실행 후 실제 상태가 다를 수 있음을 처리한다. 취소/시간 초과 후 자동 재실행하지 않는다.
15. 구성에서 서비스 제거가 자동 볼륨 삭제로 이어지지 않는다. 남은 런타임 자원을 분명히 표시한다.
16. 포트 검사에서 자신의 기존 바인딩을 구별하고 실행 전 재확인한다.
17. 실제 로컬 테스트용 프로젝트로 단독 Redis, 다중 서비스, 변경 후 재생성, DB 데이터 유지, 실패 후 수정 흐름을 검증한다.
18. 최소 창 크기, 한국어/영어, 다크/라이트, 키보드만으로 추가·연결·수정·검토·되돌리기를 완료한다. 캔버스 조작의 폼/목록 대안을 제공한다.
19. 작업 중 앱 종료 후 재시작하면 결과 미확정 기록을 실제 상태와 대조한다. 이전 명령을 자동 재실행하거나 출력 전문을 저장하지 않는다.
20. 분류되지 않은 env·command·build args·URL과 미저장 원문이 일반 자동 복원 파일에 들어가지 않는다. 원문 저장/손실 경계는 사용자에게 표시한다.

## 18. 개발 묶음과 위임

이 변화는 프로젝트 편집기·Compose 모델·장기 작업을 포함하는 기능 단위다. 색상/버튼 정리 수준의 수정으로 취급하지 않는다. 다음은 구현 순서의 큰 경계이며 세부 작업 계획은 설계 검토 뒤 작성한다.

1. 초안/서비스/네트워크/저장소 모델 + 원문 보존 + 실행 모델 분리.
2. 카탈로그/이미지 선택/내 앱 추가 + 연결 제안과 변수·시작 조건 편집.
3. 가져오기 검사/수정 + 변경 검토/실행/실패 복구 + 대표 시나리오 실검증.

초기 완성 범위는 세 묶음을 모두 포함한다. 첫 두 묶음의 화면만 만든 상태를 완료로 표시하지 않는다. 상세 DTO 이름, 세부 컴포넌트 분해, 공급자 캐시 TTL, 초기 배치 알고리즘은 구현자에게 위임한다. 기본 색/간격/컨트롤은 기존 디자인 시스템을 따른다. 승인되지 않은 기능 범위 확장과 임의의 최신 이미지 선택은 위임에 포함하지 않는다.

## 19. 구현자 관점 검토에서 보완한 결정

별도 검토자는 앱 종료 뒤 작업 수명과 임의 원문의 비밀값 보관 경계를 질문했다. 설계자는 초기 범위의 일관성을 위해 별도 실행 서비스 없이 종료 시 CLI 정리/다음 실행 시 재조회, 민감할 수 있는 원문의 자동 저장 제외를 제안으로 명시했다. 이는 사용자에게서 새로 받은 요구가 아니다.
