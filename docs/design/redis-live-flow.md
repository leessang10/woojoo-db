# Redis Live Flow 설계

작성: 2026-10-25 · 상태: 검토 가능한 설계안, 제품 코드 미구현

## 목적과 확정된 요구

Redis에 저장된 값을 읽는 화면에서 나아가, 데이터의 흐름과 생명주기를 눈으로 이해하는 작업 공간을 만든다.

- 사용자는 React Flow에서 큐의 이벤트/job이 실제로 들어오고 나가는 모습을 보고 싶다.
- 큐는 원통 형태이며 내부에 작업이 생기고 쌓이고 빠져나가는 모습을 표현한다.
- 캐시의 조회·갱신·만료를 관찰하고 캐시 설계가 제대로 작동하는지 판단하고 싶다.
- 장기간 방치되었을 가능성이 있는 키를 발견할 수 있어야 한다.
- Pretendard, 공통 shadcn UI, 간결한 카피, 자연스러운 개행, 역할별 색상과 화면 위치 유지라는 개인 선호를 따른다.

이하 화면 상세, 수집 주기, 보관량과 단계 구분은 구현을 위한 제안이다. 실제 사용 중인 큐 라이브러리와 서비스 언어는 아직 확인되지 않았다. BullMQ 사용을 전제하지 않는다.

## 접근 방식

| 방식 | 가능한 경험 | 제약 |
| --- | --- | --- |
| 스냅샷 조회만 사용 | 별도 서비스 수정 없이 값·TTL·목록 변화를 표시 | 조회 사이에 발생한 유입/유출을 놓침. hit/miss·성공/실패 확정 불가 |
| 서비스 이벤트만 사용 | 작업 ID와 키별 접근, 워커, 결과를 정확히 연결 | 서비스 연동 전에는 동작하지 않음. 이벤트 누락/중복 처리 필요 |
| 혼합 방식 — 제안 | 스냅샷으로 현재 상태, 이벤트로 변화와 업무 의미를 설명 | 두 출처를 구분하고 재연결 시 상태를 대조해야 함 |

혼합 방식을 권장한다. 스냅샷만 있는 경우에도 쓸 수 있지만, 사용자 목표인 짧게 존재하는 job의 유입·처리와 캐시 적중을 충족하려면 이벤트 연동까지 필요하다. 1단계 관측 화면을 전체 목표의 완료로 간주하지 않는다.

## 공통 화면

기존 Redis 작업 공간과 연결 프로필·저장한 보기를 유지한다. 캐시/큐는 기본 보기를 `흐름`으로 하고 `목록` 전환을 제공한다. 키 탐색 화면은 현재 구조를 유지한다.

상단: 보기 선택, 흐름/목록, 관찰 시작/중지, 화면 맞춤. 보조 메뉴: 조회 주기, 표시 수, 이벤트 연결, 모션 감소.

캔버스 왼쪽은 기존 탐색 사이드바, 중앙은 React Flow, 오른쪽 상세는 선택했을 때만 연다. 아래 최근 이벤트 영역은 기본 접힘으로 둔다. 960×640에서는 상세를 열 때 캔버스 대신 상세를 보여주고 닫으면 같은 뷰포트로 돌아간다.

상태는 `조회 관찰 · 2초 간격`, `이벤트 연결됨`, `연결 끊김 · 마지막 수신 14:32`처럼 짧게 표시한다. 상세에서 출처·표본 범위·누락을 확인한다. 상시 안내문을 늘어놓지 않는다.

뷰포트와 노드 위치는 갱신으로 바뀌지 않는다. 자동 배치는 최초 표시 또는 사용자가 요청했을 때만 실행한다. 노드 선택·키보드 탐색·상세 열기·목록 보기로 같은 정보에 접근할 수 있게 한다.

## 큐: 원통과 job

### 형태

기본 원통은 **가로로 누운 반투명 관**이다. 양 끝을 타원으로 그리고 중간 몸통을 연결해 실제 통로처럼 보이게 한다. 원통 내부에 job 카드가 순서대로 놓인다. 단순히 큐 아이콘 하나를 가운데 그리는 방식은 채택하지 않는다.

```text
관측된 유입       ╭──────────────────────────────╮       관측된 유출
   job →        (│ job 104 │ job 103 │ job 102  │)      → job
                 ╰──────────────────────────────╯
                        emails · 128개
```

- 새 작업은 입구에서 등장해 원통 안의 자리로 이동한다.
- 작업이 꺼내졌다는 이벤트가 있으면 출구를 통과한다. 워커가 확인되면 해당 워커 노드로 이동한다.
- job ID가 없는 유입/유출 알림은 익명 입자로 표현한다. 임의의 기존 job 카드와 연결하지 않는다.
- 실제 작업 ID가 있는 경우 카드에 짧은 ID·작업명을 표시하고 클릭하면 payload와 이력을 연다.
- 화면에 보이는 개별 카드는 기본 최대 12개. 나머지는 `+116`으로 묶는다. 부분 미리보기 개수와 Redis에서 읽은 전체 길이를 구분한다.
- 원통 내부가 꽉 차도 전체 큐 용량이 찼다는 의미는 아니다. 설정된 용량이 없으면 채움 비율을 용량 사용률로 표시하지 않는다.
- List의 좌/우 끝과 실제 push/pop 방향을 설정 또는 이벤트로 확인한다. 모르면 좌측/우측으로 표시하고 생산자·소비자 또는 FIFO를 추정하지 않는다. 일반적인 FIFO 모형은 설명용일 뿐이다.
- 고빈도 이벤트는 `+24 유입`처럼 묶어 이동한다. 애니메이션을 모두 재생하느라 실시간 상태가 뒤처지지 않게 한다.

### 자료형별 의미

**List:** 길이와 제한된 양 끝 구간을 조회한다. 인덱스는 이동하므로 job ID로 사용하지 않는다. 값이 같은 항목이 여러 개일 때도 임의로 같은 작업이라고 추정하지 않는다. 안정적인 ID가 없는 스냅샷 차이는 개수/구간 변화만 표현하고 특정 job의 이동 경로는 만들지 않는다. 미리보기 구간 밖으로 밀려난 항목을 dequeue로 단정하지 않는다.

**Streams:** 원통은 보존된 이벤트 로그이며 소비자 그룹별 전달 상태를 옆에 표시한다. Stream ID는 안정적인 식별자다. ACK 후에도 원본 엔트리는 남을 수 있으므로 ACK 애니메이션이 원통에서 원본 이벤트를 삭제하면 안 된다. 그룹에 전달되는 별도의 토큰을 움직이고, 그룹의 ACK 상태와 원본 로그 보존을 분리한다. 여러 그룹의 같은 ID는 서로 다른 전달이다.

**라이브러리/서비스 연동:** 의미 있는 상태 이벤트가 확인될 때만 `대기 → 처리 중 → 성공/실패/재시도` 경로를 추가한다. Worker 노드는 확인된 소비자만 표시한다. List의 POP나 Stream의 ACK만으로 업무 성공을 확정하지 않는다. Pending 목록에서 사라짐도 조회 범위·그룹 변경·관리 작업 때문에 발생할 수 있어 ACK로 추정하지 않는다.

### 모션과 색

유입은 청색 강조, 전달은 중립 이동, 확인된 완료는 초록 체크, 실패는 빨강과 실패 아이콘, 재시도는 호박색과 반복 아이콘으로 구분한다. 상태 색은 버튼의 등록/삭제 색 의미와 혼동하지 않도록 라벨을 함께 쓴다.

개별 이동 350~600ms를 초기값으로 제안한다. 지속적인 깜빡임은 피한다. 모션 감소 설정에서는 이동 대신 개수 변화·일시 강조·이벤트 이력으로 동일한 정보를 제공한다. 재연결 직후 발견된 기존 job은 새로운 유입처럼 움직이지 않는다.

## 캐시: 생명주기와 사용 흐름

패턴별 그룹 노드(`product:*`, `user:*`) 안에 키 카드를 배치한다. 기본은 그룹 요약, 선택 시 개별 키로 펼친다. 실제 서비스 이벤트에 서비스/호출자 정보가 있을 때만 요청 노드와 흐름선을 추가한다. 패턴만 보고 DB·API·사용자 사이의 관계를 만들지 않는다.

| 근거 | 화면 표현 |
| --- | --- |
| 관찰 시작 때 존재하는 키 | 강조 없이 초기 배치 |
| 이후 새로 발견한 키 | 등장 효과 + `새로 발견` |
| 생성 이벤트 | 등장 효과 + `생성` |
| 서비스의 hit 이벤트 | 요청 노드에서 키로 짧은 펄스, 관측 hit 증가 |
| 서비스의 miss 이벤트 | 키 조회 경로에 miss 표시. 값이 없는 키를 저장된 키처럼 만들지 않음 |
| 값 변경 확인 | 카드 테두리를 잠깐 강조, 마지막 변경 시각 갱신 |
| 쓰기 이벤트만 확인 | `갱신 요청/쓰기 관측`; 내용이 달라졌다고 단정하지 않음 |
| 만료 예정 시각이 유의하게 뒤로 이동 | TTL 연장 강조. 단순한 자연 감소는 갱신 이벤트가 아님 |
| TTL 0 예상 | 흐리게 표시 + `만료 예상`, 확인 전 제거하지 않음 |
| 만료/삭제 이벤트 | 이유를 표시하고 퇴장 |
| 조회로 부재 확인 | `사라짐`, 만료와 삭제는 구분하지 않음 |

TTL 바는 이번 관측에서 알려진 만료까지의 남은 시간을 표현한다. 최초 TTL을 모르면 전체 수명 비율이라고 표시하지 않는다. 무기한 키는 `만료 없음`, 권한 부족은 `확인 불가`로 표시한다.

값 미리보기 일부가 같다는 이유로 전체 값이 변하지 않았다고 단정하지 않는다. 작은 전체 값만 제한 내에서 비교하고, 대형/부분 값은 `표시 구간 변경` 또는 변경 확인 불가로 기록한다. 관측 데이터와 원문 payload를 자동으로 디스크에 저장하지 않는다.

### 방치 후보 찾기

자동으로 `불필요한 키` 판정을 내리지 않는다. 사용자가 관측 기간과 기준을 선택해 점검 후보를 강조한다.

- `만료 없음`: 상태 자체만 표시, 문제로 단정하지 않음.
- `변경 관측 없음`: 관찰 시작 이후 값/TTL 변화가 관측되지 않음. 조회가 없었다는 의미가 아님.
- `조회 관측 없음`: 서비스 접근 이벤트가 연결된 기간/대상에서 조회가 관측되지 않음. 일부 서비스만 연동된 경우 그 범위를 표시.
- `갱신 집중`: 단위 시간 내 쓰기 이벤트/확인된 변경이 기준 초과. 동일값 쓰기와 실제 값 변경을 구분.
- `miss 집중`: 키/패턴의 hit와 miss를 모두 계측할 때만 계산. 해당 관측 구간의 분모와 표본/누락 표시.

임계값은 설정 가능하며, 예를 들어 30분 관찰한 화면에서 `24시간 미사용`을 주장하지 않는다. 메모리 비용은 별도 측정이 있을 때만 표시한다. 서버 INFO 누적 hit/miss를 키별·패턴별 적중률로 바꾸지 않는다.

## 수집과 정확성

### A. 스냅샷 관측

기존 `redis_scan`, `redis_key_metadata`, `redis_read_value`, `redis_queue_inspect`를 재사용/확장한다. 정확한 키와 등록 패턴을 대상으로 관찰을 시작한다. 전체 DB를 1초마다 SCAN하지 않는다.

초기값 제안: 활성 큐 메타데이터/선택 키 2초, 알려진 캐시 키 메타데이터 5초, 패턴 탐색은 예산을 제한한 점진 순회 15초 이상. 느린 요청은 중첩하지 않고 backoff한다. 응답 크기와 시간 예산은 기존 제한을 유지한다. 스냅샷은 여러 명령 사이의 원자성을 보장하지 않는다.

기존 요청의 generation/session 검사를 확장해 이전 프로필 결과를 버린다. 재연결·필터 변경·관찰 시작은 새 기준선을 만든다. 최초 동기화에서 대량 생성/삭제 효과를 재생하지 않는다. SCAN 중 누락이나 조회 오류를 키 삭제로 해석하지 않는다. 정확한 키 존재 조회 또는 출처가 확인된 이벤트로 부재를 판정한다.

### B. Keyspace 알림 — 선택적 보강

이미 활성화되고 권한이 있는 서버에서 전용 Pub/Sub 연결로 구독한다. 설정은 자동 변경하지 않는다. 지원 이벤트와 Redis 버전을 확인하고, 허용된 관측 종류를 capabilities로 전달한다.

알림은 변경된 키와 작업 종류를 알려주지만 job payload/업무 결과/일반적인 키별 hit 전체를 제공하지 않는다. 여러 항목을 넣는 명령의 알림을 job 하나로 계산하지 않는다. 연결이 끊긴 기간의 알림은 유실될 수 있고 만료 알림은 TTL 0 시점과 정확히 일치하지 않을 수 있다. 따라서 수신 후 필요한 범위만 다시 읽고, 연결 복구 시 스냅샷으로 대조한다.

MONITOR는 기본 수집 경로로 사용하지 않는다. 모든 명령을 감시하는 부하와 노출 범위가 크고 성공/실패 응답까지 보장하는 업무 이벤트 스트림이 아니다.

### C. 서비스 이벤트/큐 어댑터 — 목표 완성을 위한 연동

라이브러리와 무관한 입력 계약을 먼저 정한다. 생산자/워커/캐시 래퍼가 업무 처리 후 이벤트를 발행하고 앱은 독립 관측 경로로 읽는다. 가능한 전송안은 별도의 관측용 Redis Stream을 **XREAD로만** 읽는 방식이다. 관측 앱은 업무 큐의 XREADGROUP/POP/XACK/CLAIM을 실행하지 않는다. 관측 Stream 생성·쓰기·보존 설정은 서비스 연동 작업의 범위다.

공통 필드: eventId, sourceId, sourceSequence(가능한 경우), occurredAt, receivedAt, profile/DB 범위, keyBase64, kind, queueKind, jobId/streamId, group, consumer, attemptId, operationId, outcome, sampling/coverage. payload는 선택적 요약만 보내고 상세 조회와 분리한다. Redis의 큰 정수/Stream ID는 문자열로 보존한다.

중복 이벤트는 eventId로 제거한다. 작업은 queue+jobId+attemptId, Stream 전달은 key+group+streamId로 구분한다. sourceSequence가 없거나 시계가 어긋나면 출처 간 전역 순서를 보장하지 않는다. 늦은 이벤트는 이력에는 남기되 최신 상태를 과거로 되돌리지 않는다. 정확히 대응되는 ID가 없으면 카드 이동을 만들어내지 않는다.

전송 누락/Stream trim/재연결 공백을 기록하고 관측 적중률·시간당 처리량의 범위를 제한한다. 이벤트 미연동 상태에서는 미지원 지표를 0으로 표시하지 않는다. 관측 앱 자체 조회는 서비스의 조회/hit 이벤트로 집계하지 않는다. 서버 전체 INFO 지표에는 앱의 조회도 영향을 줄 수 있음을 상세에 표시한다.

BullMQ를 실제 사용한다면 공식 이벤트/API에 기반한 어댑터를 후속 구현한다. 내부 키 이름만으로 라이브러리/작업 상태를 자동 추정하거나 조작하지 않는다.

## 렌더링과 모듈

React Flow는 현재 설치된 `@xyflow/react`를 재사용한다. 원통은 커스텀 노드 내부 SVG/HTML로 그리고 job은 그 내부의 경량 카드로 표현한다. 이동 토큰은 화면상 한정된 overlay로 처리하여 이벤트마다 전체 그래프를 재배치하지 않는다. 캐시 그룹/큐/확인된 worker를 React Flow 노드로 사용한다.

초기 예산 제안: 펼쳐진 키 노드 200개, 원통당 개별 job 12개, 동시 이동 토큰 30개, 메모리 이력 최근 10분/5,000건/16MiB 중 먼저 도달한 상한. 초과분은 집계하고 `일부 표시`를 알린다. 이벤트 수신은 즉시 수집하되 화면 상태는 100~250ms 단위로 합친다. 수치는 실제 부하 테스트 후 조정한다.

```text
src/redis/flow/
  RedisFlow.tsx          공통 React Flow 캔버스, 뷰포트와 선택
  QueueCylinder.tsx      원통, job 카드, 방향/집계 표시
  CacheNode.tsx          캐시 상태와 TTL
  FlowInspector.tsx      선택 데이터·근거·관측 이력
  observation.ts        출처별 이벤트 타입, capabilities
  reducer.ts            중복·지연·세션 처리, 제한된 상태/이력
  animation.ts          상태 변경에서 시각 효과 생성, 모션 감소
src-tauri/src/redis/
  observation.rs        관측 시작/중지와 읽기 예산
  notifications.rs      선택적 keyspace 전용 구독
```

관측 중지는 연결과 타이머를 정리하고 마지막 화면은 관측 시각과 함께 남긴다. 숨겨진 작업 공간에서는 수집을 중지하는 기존 정책을 유지하며, 돌아오면 공백을 표시하고 다시 동기화한다. 백그라운드 장기 모니터링은 이번 범위가 아니다.

## 구현 단계와 완료 기준

1. **원통/캐시 캔버스:** 명확히 표시된 시뮬레이션으로 생성·이동·퇴장·TTL 모션을 검토한다. 흐름/목록 전환, 상세, 테마·언어·좁은 폭 지원.
2. **실제 스냅샷 관측:** 연결된 Redis의 큐/캐시 상태를 반영한다. 부분 범위, 변화 미확인, 재연결 기준선 처리. 이 단계는 실제 처리 이벤트 전체를 보장하지 않는다.
3. **이벤트 연동:** 선택적 keyspace 구독과 사용 중인 서비스/큐 어댑터를 연결한다. 짧은 job도 수신 이벤트 기준으로 시각화하고 캐시 hit/miss·worker 결과를 연결한다. 큐 종류와 서비스 언어를 이 단계 전에 확정한다.

완료 검증은 격리된 Redis와 테스트 생산자/워커로 한다.

- job ID별 유입/처리/재시도와 화면 이력이 대응한다. 동일 payload를 가진 별개 job을 합치지 않는다.
- List의 같은 길이에서 교체된 항목, 미리보기 범위 이탈, 방향 미설정을 잘못된 성공으로 표현하지 않는다.
- Stream의 그룹별 처리와 원본 보존을 분리한다. ACK 후 원본 카드가 삭제되지 않는다.
- 캐시 생성, 동일값 쓰기, 실제 값 변경, TTL 연장, 만료, 수동 삭제를 근거 수준에 맞게 구분한다.
- 연동하지 않은 조회/hit/miss는 알 수 없음이며 서비스 계측이 있는 경우만 활성화된다.
- 중복·역순·유실·재연결, ACL 거절, 대형 값, 고빈도 이벤트에서 상태와 메모리 상한을 검증한다.
- 키보드와 모션 감소에서도 정보가 전달된다. 갱신 후 확대·이동·선택이 유지된다.
- 한국어/영어·라이트/다크·960×640에서 실제 화면을 확인한다.
